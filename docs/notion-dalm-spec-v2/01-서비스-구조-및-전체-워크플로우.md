# 01. 서비스 구조 및 전체 워크플로우

## 1. 핵심 사용자 흐름

```text
오늘의 사진 촬영 또는 선택
→ 4:5 비율 편집
→ AI 사진 적합성 검사
→ 최대 7일간 닮은 사진 탐색
→ 평행한 순간 발견
→ 두 사진과 매칭 이유 공개
→ 상대방에게 엽서 보내기
→ 순간과 엽서 보관
```

---

## 2. 전체 시스템 구조

```mermaid
flowchart LR
    U[사용자] --> F[Flutter]
    F -->|REST API + JWT| B[FastAPI]
    B --> DB[(PostgreSQL)]
    B --> S[(Private Object Storage)]
    B -->|검사·특징 추출·매칭 작업| Q[Redis / Celery]
    Q --> A[PyTorch Worker]
    A -->|이미지 조회| S
    A -->|AI 결과 반환| B
    B -->|상태·결과 저장| DB
    B --> V[(Vector Index)]
    B --> N[FCM]
    N --> F
```

> Flutter는 AI Worker, DB, Storage에 직접 접근하지 않는다. Backend가 인증·권한·상태·트랜잭션을 소유한다.

---

## 3. 파트별 책임

| 파트 | 담당 |
|---|---|
| Flutter | 온보딩, 카카오 로그인 UI, 권한 요청, 촬영·선택, 4:5 크롭, 업로드, 상태·결과·엽서 화면, 푸시 처리 |
| Backend | 카카오 토큰 검증, JWT, 사진 저장, 일일 제한, 작업 큐, 상태 전이, 후보 필터링, 매칭 트랜잭션, 엽서·신고·차단·알림 |
| AI | 적합성 검사, 특징 추출, 임베딩, 후보 재정렬 점수, 매칭 설명 데이터 생성, 모델 버전 관리 |
| PostgreSQL | 계정, 사진 메타데이터, AI 결과, 매칭, 엽서, 알림, 차단, 신고 저장 |
| Object Storage | 4:5 원본과 썸네일 저장 |

## 4. 사진 등록부터 탐색 시작까지

```mermaid
sequenceDiagram
    autonumber
    actor U as 사용자
    participant F as Flutter
    participant B as FastAPI
    participant S as Storage
    participant D as PostgreSQL
    participant Q as Queue
    participant A as PyTorch Worker

    U->>F: 촬영 또는 갤러리 선택
    F->>F: 4:5 크롭·회전 보정·최소 해상도 검사
    F->>B: POST /v1/photos
    B->>D: 오늘 활성 사진 존재 여부 확인
    B->>B: MIME·크기·이미지 검증, EXIF GPS 제거
    B->>S: 비공개 이미지 저장
    B->>D: Photo 생성 - VALIDATING
    B->>Q: 적합성 검사 작업 등록
    B-->>F: 202 + photo_id

    Q->>A: 이미지 적합성 검사
    A-->>B: 통과 또는 거절 사유

    alt 통과
        B->>D: Photo - SEARCHING
        B->>Q: 특징 추출·후보 탐색 작업 등록
        B-->>F: 탐색 시작 상태
    else 정책 거절
        B->>D: Photo - REJECTED
        B-->>F: 구체적 거절 사유 1개
    else AI 장애
        B->>Q: 정책에 따라 자동 재시도
        B-->>F: 일시적 처리 오류
    end
```

## 5. AI 후보 탐색과 매칭 확정

```mermaid
sequenceDiagram
    autonumber
    participant B as FastAPI
    participant Q as Redis/Celery
    participant A as PyTorch Worker
    participant V as Vector Index
    participant D as PostgreSQL
    participant N as FCM

    Q->>A: photo_id·storage_key 전달
    A->>A: 장면·객체행동·구도·색감·분위기 특징 추출
    A-->>B: 임베딩·라벨·AI 제목
    B->>D: PhotoEmbedding 저장
    B->>V: 활성 사진 상위 후보 검색
    V-->>B: 최근 7일 후보 ID 목록
    B->>D: 본인·차단·MATCHED·기간 만료 후보 제거
    B->>A: 후보 쌍 재정렬 요청
    A-->>B: 요소별 점수·최종 점수·설명 데이터

    alt 임계값 이상 후보 존재
        B->>D: 두 Photo 행 잠금
        B->>D: 여전히 SEARCHING인지 재검증
        B->>D: Match 생성 + 양쪽 Photo MATCHED
        B->>D: 양쪽 Notification 생성
        B->>N: 매칭 완료 푸시 2건
    else 후보 없음
        B->>D: SEARCHING 유지
    end
```

> 🔒 매칭 직전에 두 사진을 다시 확인하고 잠가야 한다. 그래야 같은 사진이 동시에 여러 사진과 매칭되는 것을 방지할 수 있다.

## 6. 7일 탐색 종료

```mermaid
flowchart TD
    S[SEARCHING 사진] --> C{search_expires_at 지났는가?}
    C -->|아니요| K[새 사진 등록 시 다시 후보 비교]

    M -->|아니요| X[EXPIRED 처리]
    X --> N[탐색 종료 알림]
```

## 7. 엽서 흐름

```mermaid
sequenceDiagram
    actor A as 먼저 사진을 등록한 사용자
    participant B as Backend
    actor C as 나중에 사진을 등록한 사용자

    A->>B: 엽서 발송 1회
    B->>B: 매칭 관계·차단·글자 수·중복 발송 검증
    B-->>C: 엽서 수신 알림
    C->>B: 답 엽서 발송 1회
    B->>B: 상대의 첫 엽서 발송 여부와 중복 검증
    B-->>A: 엽서 수신 알림
```

> 기획 정책상 먼저 사진을 등록한 사용자가 먼저 엽서를 보낸 후, 나중 사용자가 답 엽서를 보낼 수 있다. 해당 정책은 UI와 서버가 동일하게 적용해야 한다.
