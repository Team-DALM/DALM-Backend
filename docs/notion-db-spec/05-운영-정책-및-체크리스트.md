# 05. 운영 정책 및 개발 체크리스트

## 1. 보안 및 개인정보

- [ ] 비밀번호는 평문으로 저장하지 않는다.
- [ ] Object Storage 버킷을 공개하지 않는다.
- [ ] 이미지 접근에는 만료 시간이 있는 서명 URL을 사용한다.
- [ ] 모든 사진 조회·수정·삭제에서 소유권을 검사한다.
- [ ] 파일 확장자와 실제 MIME 타입을 함께 검사한다.
- [ ] 로그에 JWT, 비밀번호, 서명 URL을 기록하지 않는다.
- [ ] EXIF 위치정보 제거 여부를 확정한다.
- [ ] 탈퇴 시 개인정보와 사진 삭제 범위를 정의한다.
- [ ] 관리자 원본 사진 접근 권한을 분리한다.

> ⚠️ 사진에는 얼굴과 위치정보가 포함될 수 있으므로 일반 게시물 텍스트보다 높은 수준의 접근 통제가 필요하다.

## 2. 삭제 정책

| 데이터 | 권장 방식 | 설명 |
|---|---|---|
| 게시물 | 소프트 삭제 | 신고·운영 기록 보존 |
| 댓글 | 소프트 삭제 | 대댓글 관계 유지 |
| 좋아요 | 물리 삭제 | 복구 필요성이 낮음 |
| 알림 | 보존 기간 후 물리 삭제 | 보존 기간 합의 필요 |
| 사진 원본 | Object Storage에서 물리 삭제 | 개인정보 포함 가능 |
| 썸네일 | 원본과 함께 물리 삭제 | 파생 파일 삭제 필요 |
| 분석 결과 | 사진 정책에 따라 삭제 | 통계 사용 시 익명화 검토 |
| 사용자 | 비식별화 또는 물리 삭제 | 서비스 정책 확정 필요 |

### 삭제 시 확인 대상

```text
사진 원본
├─ 썸네일
├─ 분석 작업
├─ 분석 결과
├─ 게시물 참조
└─ Object Storage 백업 및 캐시
```

---

## 3. 트랜잭션

### 게시물 작성

```text
사진 소유권 확인
→ 분석 결과와 사진 관계 확인
→ 게시물 생성
→ COMMIT
```

하나라도 실패하면 전체 작업을 롤백한다.

### 좋아요 등록

```text
좋아요 INSERT
→ DB 알림 INSERT
→ COMMIT
→ FCM 전송 작업 등록
```

FCM처럼 외부 시스템에 대한 요청은 DB 트랜잭션 안에서 기다리지 않는다.

## 6. 완료 조건

- [ ] ERD 리뷰가 완료되었다.
- [ ] 모든 테이블의 PK와 FK가 정의되었다.
- [ ] Nullable 여부와 기본값이 정의되었다.
- [ ] UNIQUE 및 CHECK 제약조건이 정의되었다.
- [ ] 주요 조회 조건에 대한 인덱스가 정의되었다.
- [ ] 사진 업로드와 AI 분석이 비동기로 분리되었다.
- [ ] 모델 이름과 버전이 분석 결과에 저장된다.
- [ ] AI 입력·출력 JSON 구조가 합의되었다.
- [ ] Flutter가 사용할 상태와 오류 코드가 공유되었다.
- [ ] API별 입력, 출력 및 접근 권한이 정의되었다.
- [ ] 이미지와 개인정보 삭제 정책이 확정되었다.
- [ ] Alembic 마이그레이션으로 스키마를 재현할 수 있다.
- [ ] 주요 기능의 테스트 케이스가 작성되었다.

## 8. 회의 리뷰 질문

### Frontend에 확인

- 상태별 화면과 문구가 정의되어 있는가?
- 업로드 진행률을 표시해야 하는가?
- 푸시 알림이 없을 때 상태를 어떻게 갱신할 것인가?
- 분석 결과 중 어떤 필드가 화면에 필요한가?

### AI 파트에 확인

- 최종 감정 라벨과 점수 범위는 무엇인가?
- 전처리 입력 크기와 포맷은 무엇인가?
- 예상 평균·최대 추론 시간은 얼마인가?
- CPU와 GPU 중 어떤 환경이 필요한가?
- 재시도해도 되는 오류를 구분할 수 있는가?

### Backend에서 확인

- 요청별 소유권 검사가 정의되어 있는가?
- 중복 분석 요청을 어떻게 처리할 것인가?
- 작업이 중단됐을 때 타임아웃 처리가 있는가?
- 이미지와 관련 파생 데이터가 함께 삭제되는가?
- 모델 버전 변경 후 재분석 정책이 있는가?
