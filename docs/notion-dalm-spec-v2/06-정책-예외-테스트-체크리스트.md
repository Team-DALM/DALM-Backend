# 06. 정책·예외·테스트 체크리스트

## 1. 주요 정책 검증

### 하루 한 장

- [ ] 동일 사용자가 같은 날짜에 활성 사진 2장을 만들 수 없다.
- [ ] `REJECTED` 사진 후에는 같은 날 재등록할 수 있다.
- [ ] `SEARCHING` 사진 삭제 후에는 같은 날 재등록할 수 있다.
- [ ] `MATCHED` 사진은 교체할 수 없다.
- [ ] 사용자 시간대 경계에서 날짜가 정확히 계산된다.

### 7일 탐색

- [ ] 등록 즉시 `search_expires_at`이 설정된다.
- [ ] 7일 내 과거 `SEARCHING` 사진이 새 사진과 비교된다.
- [ ] 본인 사진은 후보에서 제외된다.
- [ ] 차단 관계는 양방향으로 제외된다.
- [ ] `MATCHED`, `EXPIRED`, `DELETED` 사진은 제외된다.
- [ ] 임계값 이상 후보가 없으면 `SEARCHING`을 유지한다.
- [ ] 만료 시 정확히 `EXPIRED`로 변경된다.

### 사진당 한 번 매칭

- [ ] 같은 사진에 동시 매칭 요청을 발생시켜도 Match는 하나만 생성된다.
- [ ] 두 사진 상태 변경과 Match 생성이 한 트랜잭션이다.
- [ ] 매칭 직전 삭제가 발생하면 삭제 또는 매칭 하나만 성공한다.
- [ ] 차단 직전 매칭은 서버 커밋 순서에 따라 일관되게 처리된다.

### 엽서

- [ ] 매칭 참여자만 보낼 수 있다.
- [ ] trim 후 1~200자만 허용한다.
- [ ] 사용자별·매칭별 한 번만 보낼 수 있다.
- [ ] 발송 순서 정책을 서버가 검증한다.
- [ ] 발송 후 수정과 재발송이 불가능하다.
- [ ] 차단 후에는 새 엽서를 보낼 수 없다.
- [ ] 중복 API 호출에도 한 장만 생성된다.

## 2. 주요 예외 처리

| 상황 | 처리 |
|---|---|
| 네트워크 단절 | 오프라인 안내, 안전한 요청만 재시도 |
| 업로드 실패 | Flutter 선택·편집 상태 유지, 재시도 제공 |
| AI 검사 장애 | 정책 거절과 구분, 자동 재시도 후 안내 |
| 특징 추출 실패 | SEARCHING 진입 전 재시도 또는 시스템 오류 처리 |
| 매칭 직전 삭제 | Photo 행 잠금으로 삭제·매칭 중 하나만 성공 |
| 동시 중복 매칭 | `UNIQUE(photo_id)`와 트랜잭션으로 하나만 확정 |
| 엽서 중복 발송 | `UNIQUE(match_id, sender_id)`로 방지 |
| 차단 직전 엽서 | 트랜잭션 처리 시점의 차단 상태를 기준으로 결정 |
| 상대 탈퇴 | 익명 사용자 및 삭제 이미지로 대체 |
| 푸시 권한 거부 | 앱 내 알림은 정상 유지 |
| FCM 실패 | DB 알림 유지, 전송 재시도 |

## 3. 보안 및 개인정보

- HTTPS와 JWT 인증
- Refresh Token 별도 저장·폐기 정책
- Private Object Storage와 만료 서명 URL
- EXIF GPS 제거
- 확장자와 실제 MIME 타입 검사
- 정확한 위치·연락처·카카오 친구 목록 미수집
- AI 분석 목적을 개인정보 처리방침에 명시
- 로그에 토큰·서명 URL·엽서 전문을 불필요하게 기록하지 않음
- 신고 운영자의 이미지 접근 기록 관리
- 회원 탈퇴와 삭제 요청에 대한 원본·썸네일·캐시 삭제 범위 정의

| 일반 API | 2초 이내 |

## 8. MVP 성공 기준

- [ ] 로그인부터 첫 사진 등록까지 정상 완료된다.
- [ ] AI 검사 결과와 대표 거절 이유를 확인할 수 있다.
- [ ] 사진 상태가 최대 7일 동안 정확히 관리된다.
- [ ] 과거 활성 사진과 새 사진을 양방향으로 비교한다.
- [ ] 한 사진이 여러 사진과 중복 매칭되지 않는다.
- [ ] 결과에서 두 장의 4:5 사진과 매칭 이유를 확인한다.
- [ ] 매칭된 상대에게만 사용자별 한 장의 엽서를 보낼 수 있다.
- [ ] 삭제된 탐색 사진이 후보에서 즉시 제거된다.
- [ ] 신고·차단 이후 상대 콘텐츠가 노출되지 않는다.
- [ ] 학습 모델이 단일 임베딩 Baseline보다 높은 사용자 선호도를 보인다.

## 9. 파트별 리뷰 질문

### Frontend

- 상태별 화면과 문구가 모두 매핑되었는가?
- 4:5 편집 결과의 실제 출력 크기가 합의되었는가?
- 푸시가 없을 때 앱 재진입 시 상태를 새로 조회하는가?
- 삭제·신고·차단 후 캐시 데이터를 즉시 제거하는가?

### AI

- 적합성 검사 거절 코드별 판단 기준이 있는가?
- 임베딩 차원과 정규화 방식이 확정되었는가?
- 장면 최소 점수와 최종 매칭 임계값이 분리되어 있는가?
- 모델 버전별 결과 재현이 가능한가?

### Backend

- 하루 한 장을 DB 제약으로 보호하는가?
- Photo 잠금 순서가 결정적이어서 데드락 위험을 낮추는가?
- 차단 관계를 후보 검색과 엽서 발송 모두에서 검사하는가?
- Storage 삭제와 DB 상태 변경 실패를 복구할 수 있는가?
- 만료·재시도·푸시를 위한 스케줄 작업이 정의되었는가?
